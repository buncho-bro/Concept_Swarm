# Benchmark 評価基盤開発の軌跡と技術的総括 (RETROSPECTIVE)

## 1. プロジェクトの背景と目的
`benchmark` は、Concept Swarm（概念スウォーム）および潜在空間蒸留モデルが、一般的なコード生成タスクにおいて「実用に耐えうる正確性を維持できているか」を客観的・厳格に評価するために構築された検証モジュールである。

特に、HumanEvalの上位互換でありエッジケース検証が極めて厳格な **MBPP+ (Mostly Basic Python Problems Plus)** をターゲットとし、概念蒸留プロセスがプログラミング能力（構文理解・アルゴリズム実装）に与える影響を定量評価することを目的とした。

---

## 2. 開発プロセスと主要コンポーネント

### A. 評価ワーカーと分離実行環境 (`eval_worker.py`)
- **目的:** 生成されたコードを動的に `exec()` / `pytest` で実行し、アサーションテストを通過するかを判定する。
- **課題:** 不完全なコード（無限ループ、危険なファイル操作、構文エラー）が評価プロセス全体を道連れにクラッシュさせるリスクがあった。
- **解決策:** サブプロセス化およびタイムアウト監視機構（TimeoutHandler）を導入し、サンドボックス内で安全にテストケースを実行するパイプラインを確立した。

### B. MBPP+ 実行ハーネス (`run_mbppplus_benchmark.py`)
- パイプライン全体（初期概念抽出 ➔ 潜在合議 ➔ Dual-Stream デコード ➔ コード抽出 ➔ 評価）を一気通貫で回し、Pass@1スコアを算出。
- 通常の小規模モデル単体と、Concept Swarmによる合議を経たモデルの間で、解の探索成功率がどのように向上するかを比較検証した。

---

## 3. 直面した技術的課題・失敗と解決策

### ① 概念蒸留による「文法劣化（Syntax Erosion）」の発見
- **失敗・発見:** 初期実験において、概念ベクトルのみで思考を進めたモデルは、アルゴリズムの核（Chudnovsky法や動的計画法のロジック）を完璧に把握しているにもかかわらず、インデントの乱れや変数名の typo、コロンの欠落などによって **Pass@1 が急落する** というショッキングな結果が出た。
- **分析:** 潜在空間のトポロジー最適化は「意味の正しさ」を保証するが、自己回帰型言語モデルが持つ「前後の文字の出現確率（構文的制約）」を破壊してしまうことが判明した。
- **解決策:** この発見が、`core` の **Dual-Stream Decoder**（Stream 1: 概念核 + Stream 2: 構文アンカー）および `alice_relay_engine` の **Output Bridge**（ベース状態のクリーンな小規模モデルへの注入）という最重要ブレイクスルーを生み出す直接の契機となった。

### ② Python `exec()` スコープ解決の罠
- **失敗内容:** 生成コードを `exec(code_string, globals_dict, locals_dict)` で評価する際、`globals_dict` に `{}` を渡すと、`from decimal import getcontext` などの標準インポートがローカルスコープ内の関数から見えなくなり、`NameError` でテストが不当に失敗するバグに遭遇した。
- **解決策:** Pythonのスコープ規則に従い、単一の辞書を `globals` かつ `locals` として渡す（`exec(code, scope_dict, scope_dict)`）ことで、モジュールインポートと関数定義が正しく相互参照できる環境を完成させた。

---

## 4. 総括と成果
本ベンチマーク基盤が存在したことで、「概念蒸留モデルは頭が良いが口下手（文法が崩れる）」という致命的な弱点を早期に発見・数式化でき、最終的な「潜在合議＋クリーンモデル注入（Output Bridge）」という高精度パイプラインの完成へと結実した。客観的な指標なくして、本アーキテクチャの完成はあり得なかった。
