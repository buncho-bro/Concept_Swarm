# 逆算型目標樹形図エンジン (Goal-Driven Tree Engine / GDTE v3.4) 詳細設計書
## 概念核（Concept Core）言語プリミティブ分解アーキテクチャ

---

## 1. 根本課題と哲学的背景（概念核への帰着）

### 1.1 従来の根本課題: 未定義領域と非機能語の残存
AIによるソフトウェア・ゲーム設計において、最も危険なハルシネーションは「複合機能や抽象概念のままタスクを完了と見なすこと」です。
従来のツリー展開では以下のような致命的な欠陥が生じていました：
- **未定義領域の放置:** 「勝敗判定アルゴリズム」とだけ定義され、**何をもって勝敗とするのか（計算式）**や**いつ判定するのか（実行タイミング）**が未定義のまま放置される。
- **範囲の曖昧さ:** 「元素データ」とだけ定義され、**どこからどこまで使うのか（元素のスコープ・制約）**が定義されていない。
- **抽象形容詞（お題目の罠）:** 「対象ルールの明確さ」「一貫性の担保」など、コードに落とし込めない非機能的文言が葉ノードに迷入する。

### 1.2 コア思想: 「言語上で定義されている関数に行きつくまで分解する」
> **設計原則（ユーザー提言）:**
> 「このtreeの作業というのはすでに言語上で定義されている関数に行きつくまで行われます。概念核と一緒なのですよ、AIが間の補正しかしなくてもよいぐらいまで徹底的に仕組みを作るという点で。」

GDTE v3.4では、目標樹形図を**「不変の仕様骨格＝概念核（Concept Core）」**と位置づけます。
末端の作業AI（Worker AI）にルールや構造の裁量を与えてはならず、AIが行う作業は「事前定義された組み込み関数・演算子・定数データ同士を繋ぎ合わせる『間の補正（構文的補間）』のみ」となるまで徹底的に分解し尽くします。

## 2. システムアーキテクチャ概要

```mermaid
flowchart TD
    UserReq[ユーザー指示 / ゲーム要件] --> RF[RuleFormulator: ルール詳細仕様化エンジン]
    
    subgraph SpecLayer [1. ゼロ未定義仕様の策定 (RuleFormulator)]
        RF --> ElementsSpec[元素スコープ & パラメータ辞書<br/>第1〜2周期 H, C, N, O / 原子価・親和力]
        RF --> BindingSpec[分子結合仕様<br/>手札隣接走査 & 親和力優先再結合]
        RF --> DeckSpec[デッキ仕様<br/>最大30枚 / 手札5枚 / 初期配布]
        RF --> VictorySpec[勝敗・評価基準<br/>タイミング: ターン終了時<br/>判定式: sum安定度 + 有機ボーナス >]
        RF --> UISpec[UI表示要件<br/>手札カード・結合状態 / バトルログ]
    end
    
    SpecLayer --> TA[TreeArchitect: 概念核樹形図アーキテクト]
    
    subgraph CoreTree [2. 概念核 (Concept Core) 再帰分解ループ]
        TA --> NodeQ{最深要素への問合せ<br/>組み込み関数・演算子に到達したか？}
        NodeQ -- "複合概念 / 未定義あり" --> Decomp[When / What / Scope の3次元分解]
        Decomp --> Reviewer[Reviewer / Critic: 抽象語排除 & プリミティブ検証]
        Reviewer --> NodeQ
        NodeQ -- "言語プリミティブ (sum, len, range, dict, > 等)" --> AtomicLeaf[null 返却 ➔ ATOMIC葉ノード確定]
    end
    
    AtomicLeaf --> Swarm[使い捨て作業AIスウォーム (Worker Swarm)]
    
    subgraph WorkerExec [3. 『間の補正』コード生成 & 検証]
        Swarm --> CodeGen[プリミティブ間を繋ぐグルーコード実装]
        CodeGen --> ASTVerify[AST構文解析・インポート検証]
        CodeGen --> AcceptanceBox[厳格受入テスト・実行時アサーション]
    end
    
    AcceptanceBox --> Mainline[正史コードベース (Verified Mainline)]
```

## 3. ゼロ未定義領域（Zero-Ambiguity）の3軸保証

GDTE v3.4では、すべての機能ノードに対して以下の3軸が網羅されるまで分解を強制します：

| 軸 | 検証項目 | 元素対戦カードゲームにおける具現例 |
| :--- | :--- | :--- |
| **What (基準・計算式・データ構造)** | 何を対象とし、どのような計算式・定数・テーブルで処理するか | `sum(molecule_stability)` + 有機ボーナス / 元素定数辞書 `{'H': {'valency': 1, 'affinity': 2.2}, ...}` |
| **When (タイミング・フェーズ)** | いつその処理が発火・評価されるか | ターン終了時（全手札結合確定後）、カード配置直後（隣接スキャン時）、特殊カード使用時 |
| **Scope (範囲・制約・境界)** | 対象の境界値・上限・採用範囲はどこか | 元素採用範囲（第1〜2周期: H, He, Li, Be, B, C, N, O, F, Ne）、デッキ最大30枚、初期手札5枚 |

## 4. 概念核樹形図の階層構造（Concept Core Decomposition Tree）

本システムによって導出されるツリー構造は、高レベルなゲーム構想から最末端の言語組み込み関数・演算子へと直結します：

```
node_0: [ROOT] 元素対戦カードゲーム (手札内自動分子結合・再結合・特殊カード)
├── node_1: 元素データ定義システム [BRANCH]
│   ├── node_6: 定義元素のスコープ確定 (第1〜2周期代表元素) [ATOMIC (null)] ➔ タプル定数 ('H', 'C', 'N', 'O')
│   ├── node_7: 原子価・親和力パラメータ辞書 [ATOMIC (null)] ➔ 言語組み込み dict テーブル
│   └── node_8: 元素カードオブジェクト生成 [ATOMIC (null)] ➔ クラス生成 & 初期化 __init__
├── node_2: 分子自動結合・再結合システム [BRANCH]
│   ├── node_9: 手札内隣接自動スキャン [ATOMIC (null)] ➔ for i in range(len(hand)-1) ループ
│   ├── node_10: 親和力優先の再結合アルゴリズム [ATOMIC (null)] ➔ 比較演算 (affinity_A > affinity_B)
│   └── node_11: 特殊カード効果処理 (熱: 解離, 衝撃: シャッフル) [ATOMIC (null)] ➔ pop, random.shuffle()
├── node_3: デッキ構築・手札管理システム [BRANCH]
│   ├── node_12: デッキ最大枚数制約検証 [ATOMIC (null)] ➔ len(deck) <= 30 アサーション
│   ├── node_13: 山札シャッフル機能 [ATOMIC (null)] ➔ 言語組み込み random.shuffle()
│   └── node_14: 手札初期配布・上限管理 [ATOMIC (null)] ➔ リストスライス deck[:5], len(hand) == 5
├── node_4: 対戦進行・勝敗判定アルゴリズム [BRANCH]
│   ├── node_15: 判定実行タイミング制御 (ターン終了時フック) [ATOMIC (null)] ➔ フェーズ比較 (phase == "TURN_END")
│   ├── node_16: 分子安定度スコア集計式 [ATOMIC (null)] ➔ 言語組み込み sum() + 有機ボーナス加算
│   └── node_17: 勝敗比較演算処理 [ATOMIC (null)] ➔ 比較演算子 (score_A > score_B)
└── node_5: UI・対戦ログ表示システム [BRANCH]
    ├── node_18: 手札カードおよび分子結合状態表示 [ATOMIC (null)] ➔ 文字列フォーマット print()
    └── node_19: バトルログおよび勝敗スコア表示 [ATOMIC (null)] ➔ 辞書整形 f-string 出力
```

すべての末端ノード（葉ノード）が `null`（言語組み込み関数・演算子・定数辞書レベル）に到達した瞬間に、Treeは完成と認定されます。

## 5. 作業AI（Worker AI）の「間の補正（Glue Coding）」機構

葉ノード群が完全に組み込み関数・演算子レベルまで確定しているため、Worker AI（`qwen2.5-coder:3b`）のタスクプロンプトは極めてシンプルかつ決定的になります：

```
【タスク指示】:
与えられた概念核ノードに従い、以下の言語組み込み処理を接続（間の補正）せよ。
1. 元素辞書: {'H': (1, 2.2), 'C': (4, 2.55), 'N': (3, 3.04), 'O': (2, 3.44)}
2. 結合走査: range(len(hand)-1) による隣接比較
3. スコア計算: sum(m.stability for m in molecules)
4. 勝敗判定: score_p1 > score_p2
※ アーキテクチャやルールを独自創作・推測してはならない。上記プリミティブ間の構文接続のみを行え。
```

これにより、ローカル軽量モデル（3Bクラス）であっても、一切の仕様逸脱・ハルシネーション・ダミースタブを発生させることなく、本番稼働可能な高品質コードを出力できます。

## 6. Web UI 可視化連携

本エンジンの状態は、リアルタイムWebダッシュボード（`http://localhost:8085/`）にて以下の通り即時反映されます：
1. **Domain Specification Cards:**
   - 元素スコープ & 原子価テーブル
   - 自動結合・再結合ルール
   - デッキ・手札制約
   - 勝敗判定タイミング & スコア計算式
   - UI表示要件
2. **Concept Core Tree Visualizer:**
   - ノードごとの深さ、親ノード、ステータス（BRANCH / ATOMIC (null)）
   - 各ノードが帰着した言語組み込み関数（`sum`, `len`, `range`, `dict`, `random.shuffle` 等）のバッジ表示
3. **Swarm Execution Monitor:**
   - Worker AIが「間の補正」を実行するプロセスのリアルタイムログ
   - 厳格サンドボックス（AST解析＋アサーション実行）の合否インジケータ
