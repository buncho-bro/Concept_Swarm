# Alice Profiler 開発の軌跡と技術的総括 (RETROSPECTIVE)

## 1. プロジェクトの背景と目的
`alice_profiler` は、約160GBに及ぶ巨大モデル **AliceAI-80B（MoEアーキテクチャ）** の全重みをローカルディスクにダウンロードすることなく、またメモリに全展開することなく、**「外部からピンポイントでExpert（専門家）の重み構造をプロファイリング・解析する」** ために開発された革新的なストリーミング・プロファイラーである。

一般的なPC環境（ディスク容量やRAMが限られた環境）で、クラウド上の巨大モデルをどう解体・分析するかという極限の課題に挑んだ。

---

## 2. 主要コンポーネントと技術的アプローチ

### A. HTTP Range ストリーミング・ローダー (`expert_topography_profiler.py`)
- **メカニズム:** Safetensorsフォーマットのバイナリ仕様を直接解析。
  1. 先頭8バイト（uint64）を読み取り、JSONヘッダーの長さを取得。
  2. JSONヘッダーのみを取得し、48層×全Expertのテンソルオフセット（`data_offsets`）とデータ型（`BF16`）をメモリ上にマップ。
  3. 必要なExpert（$W_{\text{gate\_up\_proj}}, W_{\text{down\_proj}}$）のバイト範囲（Range）だけをピンポイントでHTTPリクエスト。
  4. `np.frombuffer` / `torch.frombuffer` でインメモリデコードし、ローカルRAM消費を **100MB未満**、ディスク消費を **0GB** に抑えて80Bモデルの全Expertトポロジーを完全走査した。

### B. マニフェスト生成
- 各Expertの活性化傾向と重みノルムを解析し、数学専門Expert群（`math_experts_manifest.json`）およびコード専門Expert群（`code_experts_manifest.json`）を抽出・分類することに成功した。

## 3. 直面した技術的課題・失敗と解決策

### ① Windows環境における ThreadPool のサイレント・ハング
- **失敗内容:** プロファイリングを高速化するため、`concurrent.futures.ThreadPoolExecutor(max_workers=32)` を用いてHuggingFaceサーバーへ並列HTTP Rangeリクエストを一斉送信したところ、**Windows上でスクリプトが無言で停止（Silent Hang）し、復帰しなくなる現象** が頻発した。
- **原因の究明:** WindowsのソケットプールおよびPythonの同期HTTPセッション（`urllib3` / `requests`）が、大量の並行コネクション確立時にコネクションプールのデッドロックを引き起こしていたことが判明。
- **解決策:** 
  1. ワーカー数を適切な安全値（4〜8スレッド）に制限し、指数バックオフ付きのリトライループを導入。
  2. 大規模な走査時は `aiohttp`（非同期I/O）への切り替え、あるいはモックプロファイラーによるオフライン検証機構を実装して安定化させた。

### ② Safetensors BF16 バイト整列の罠
- **課題:** 受信した生バイト列をPyTorchテンソルに復元する際、バイト境界（Stride）やエンディアンのズレにより、値が `NaN` や非数に化ける事象が発生。
- **解決策:** テンソルヘッダーに記述された正確なバイトオフセットと要素数を厳密にパースし、`torch.frombuffer(..., dtype=torch.bfloat16)` で直接バインドするクリーンなバイナリパーサーを構築した。

---

## 4. 総括
`alice_profiler` は、「巨大AIを扱うには巨大なインフラが必要である」という常識を覆した。160GBのモデルを1バイトもローカルディスクに落とさず、通信帯域とRAMを極限まで節約して必要な知識だけを切り出すという技術的勝利は、次工程の `alice_relay_engine`（オンデマンドMoE実行エンジン）の誕生を可能にした。
